The steps

Genuinely sequential — each one is wasted effort until the one above it is done.

01

Get the ad account out of pause

Blocking You · Microsoft UI

The account is paused at Microsoft's end, and no code change touches this:

Name "sitetospend" Number "G120QTNQ" AccountLifeCycleStatus "Pause" PauseReason 2 CurrencyCode "AUD"

PauseReason 2 is a system pause, which in practice almost always means there is no valid payment method on the account. Sign in to Microsoft Advertising, add billing, and get the account to Active. Until then anything we deploy simply will not serve.

The account bills in AUD, but config/microsoftads.php still defaults to country_code => 'US' and EasternStandardTime. Worth switching to AU once the account is live — cosmetic next to the pause, but it will skew new campaign defaults.

02

Fix the tenant ID in production

You · Forge

This is the one that makes the API reachable at all. Production has MICROSOFT_ADS_TENANT_ID set to a tenant GUID, but your Microsoft account is a personal account, not an organizational one, so that endpoint rejects the refresh token. Tested live from production:

CONFIGURED(4e0ad749..) HTTP 400 FAIL: invalid_grant consumers HTTP 200 OK organizations HTTP 400 FAIL: invalid_grant common HTTP 200 OK

In the Forge environment editor for the site, change:

MICROSOFT_ADS_TENANT_ID=common

This one has been hiding. php artisan microsoftads:test loops through four endpoints until one works, so it reports success — but BaseMicrosoftAdsService::authenticate(), the path every real API call takes, uses only the configured tenant. A green test command has never proved the app can authenticate.

03

Add Spectra's own account IDs

You · Forge

New settings, needed by the own-site conversion fix in step 6. I have already added them to your local .env and to .env.example; production needs them too: 

SPECTRA_MICROSOFT_ADS_ACCOUNT_ID=188443253
SPECTRA_MICROSOFT_ADS_CUSTOMER_ID=255004728

Then redeploy (or run php artisan config:clear) so the cached config picks up all three env changes.

04

Turn the platform on

You · Admin

enabled_platforms.microsoft.is_enabled is false. It is checked before authentication, so every Microsoft service currently returns early no matter how good the credentials are. Flip it in the admin platforms screen, or: 

php artisan tinker --execute="\App\Models\EnabledPlatform::where('slug','microsoft')->update(['is_enabled'=>true]);"

Do this after steps 1–3, so the first thing it enables is a working path.

05

Link one customer and prove the chain

Verify

Linking is still manual (see what is still missing). Pick one customer and wire it to the ad account by hand — this proves the whole path end to end without waiting on the provisioning work: 

php artisan microsoftads:link-account \
  --customer-id=<your customer id> \
  --account-id=188443253 \
  --ms-customer-id=255004728

Then confirm the account answers and the UET tag resolves:

# lists accounts under the manager — should print sitetospend
php artisan microsoftads:refresh-token --list-accounts

# resolves and stores the customer's UET tag
php artisan microsoftads:list-uet-tags

Once that is clean, deploy a search campaign to that customer and watch for rows landing in microsoft_ads_performance_data — the hourly sync job is already scheduled and genuinely works.

06

Code bugs

Done

All four are fixed, formatted, and pass static analysis with no new baseline entries. Nothing here is deployed until you push.

  • ✓ The main deploy path was sending a campaign ID where an account ID belongs app/Services/Agents/MicrosoftAdsExecutionAgent.php — executeGoogleImport() AddImportJobs takes the Google Ads account to import from, but the code passed google_campaign_id, so every import job went up malformed. Now it reads the customer's linked Google account, strips the dashes Google displays, skips cleanly when there is no linked account, and returns the import job ID so the run can actually be followed up.
  • ✓ Conversion tracking set up a tag it then threw away app/Services/Agents/MicrosoftAdsExecutionAgent.php — executeConfigureTracking() It read $newTag['UetTagId'], which createUetTag() never returns, so the create branch always produced null and the tag was never stored on the customer. It also passed url_expression where the method reads url_contains, so the goal went up matching nothing. Now it calls resolveUetTagId(), which finds or creates the tag and persists it, with the correct key names.
  • ✓ Offline conversions created a goal per lead instead of uploading conversions app/Jobs/UploadOfflineConversions.php — uploadToMicrosoft() It called createEventConversionGoal() for every row, which defines a new conversion goal rather than recording a conversion — so a busy account would accumulate one goal per lead and never attribute anything. Now it calls applyOfflineConversion() with the row's Microsoft click ID, and skips rows that have none, since there is nothing to attribute without one.
  • ✓ Own-site conversions were sent with blank account headers app/Jobs/RecordSiteMicrosoftConversion.php It built new Customer — an empty, unsaved stub — and every SOAP call takes its CustomerId and CustomerAccountId headers from that object, so each upload reached Microsoft with both blank. It now uses Spectra's own account from config (step 3), reports the conversion at the time it happened rather than when the user signed up, and surfaces failures to the admin exception dashboard.

What is still missing

Working through steps 1–5 gets one customer live. This is what stands between that and Microsoft being a real self-serve platform alongside Google.

There is no automatic account provisioning, and this is the significant one. For Google, creating a customer fires an observer that dispatches a job to create a sub-account under your MCC and write the ID back — which is why fourteen of fifteen customers have a Google account and you have never thought about it. Microsoft has no equivalent: no provisioning job, no observer hook, no link-state column. The manager_account_id sits in config and is read by no code in the repo at all. Until a ProvisionMicrosoftAdsAccount job exists, every Microsoft customer has to be linked by hand.

Beyond that, the integration is thinner than Google's in ways worth knowing before you sell it:

  • Search campaigns only. Google has seven campaign-type executors; the Microsoft agent dispatches on actions rather than campaign types, and its extensions step is a literal no-op.
  • The optimization agent only notifies. It checks budget pacing, CTR decline, CPL and impression share, then raises a notification or a creative brief — it never changes a campaign.
  • The audience agent skips Microsoft silently. It builds audiences for Google and Facebook, with no Microsoft branch and no warning that it was skipped.
  • Health checks do not call the API. Google and Facebook have dedicated checkers that probe the live account; Microsoft only confirms a refresh token exists and that performance data is not stale.
  • Creative work is metrics-only. No ad copy is fetched or generated for Microsoft — headline and description variations are Google and Facebook paths.
  • customers.microsoft_ads_access_token is a leftover column from an abandoned per-customer OAuth design, read and written by nothing. Safe to drop.

The parts that genuinely match Google: hourly performance sync with circuit breaker and locking, UET tag provisioning into GTM, and management-account authentication — no per-customer OAuth anywhere, correctly following the architecture rule.
