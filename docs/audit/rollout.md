# Audit remediation rollout

The application changes are local until reviewed and deployed. Production settings are outside the repository.

1. Back up the database. Run the duplicate-account preflight before deploying: `SELECT customer_id, count(*) FROM ad_spend_credits GROUP BY customer_id HAVING count(*) > 1;`. The migration refuses to guess how duplicate monetary balances should be merged.
2. Apply migrations before restarting Horizon. Budget caps are backfilled from existing daily budgets. New customer confirmations update the cap; automatic recommendations cannot raise it. Existing billing run rows remain as legacy history; new settlement records use the customer's spend date, completion state and expiring lease.
3. Deploy `infrastructure/crawler/compose.yaml` on a dedicated renderer host. Chromium has no external network: only the public-web proxy has egress. Use a random renderer token of at least 32 characters, and expose the authenticated endpoint only to application workers. Configure `CRAWLER_RENDERER_URL` and `CRAWLER_RENDERER_TOKEN` on the app. Without this service, crawling uses DNS-pinned HTTP and does not execute page JavaScript; visual screenshots are unavailable. Test the container's Chromium sandbox on the target host; never add `--no-sandbox`.
4. Disable Forge's immediate push deployment. Trigger it only after the `CI` workflow succeeds, and pass that workflow's full commit SHA. In the Forge deployment script, run `bin/verify-deploy-commit "$FORGE_DEPLOY_COMMIT"` **before checkout or switching the release symlink**, and check out precisely that SHA. Provide a read-only Actions `GH_TOKEN` to the deploy process. An unavailable/pending/failed check must stop the deployment. The repository cannot prove this gate is active until the Forge configuration is changed.
5. Download an actual backup to a disposable restore host. Extract its database dump and run `bin/verify-backup-restore dump.sql.gz --port 5432 --user restore_operator`. Use a dedicated local PostgreSQL instance and a role unable to reach production. Record backup time, restore duration and the result. A local test-database drill validates the tool only; it is not evidence that the production backup is recoverable.
6. Generate the creative review manifest with `php artisan creative:benchmark --output=review.json`. Render each fixed fixture using the candidate prompts; include three distinct concepts, their file hashes, and video where requested. Review the actual outputs against the six criteria, then run `php artisan creative:benchmark review.json`. Keep the passing manifest with the release. Scores are human assessments, not promises of ad performance. The command fails when the prompt fingerprint or reviewed asset hashes change.

Stripe charge attempts retain their PaymentIntent IDs so a settled charge can be recovered without creating another payment. An uncertain response older than 23 hours requires reconciliation against Stripe; it fails closed rather than reusing a potentially expired idempotency key. Initial account and ledger writes commit together. Pre-existing accounts without their funding ledger need investigation against Stripe records; do not invent a balancing credit.

Source guidance: [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests), [Google image asset guidance](https://support.google.com/google-ads/answer/14530211?hl=en), [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).
